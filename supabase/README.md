# Private Personal HQ sync database

This folder defines a proposed Supabase/Postgres schema for authenticated private task storage. It is source-controlled because it contains schema only; private task data, resume/GST/health records, project credentials and service-role keys must never be committed.

Apply both migrations in order. The initial schema migration is read-only; the next migration adds authenticated compare-and-swap task RPCs while denying direct table writes. Do not apply only a historical or partial version. The migrations are not applied to a live project. Before doing so, create/select the owner's Supabase project, choose a region and plan, review retention and costs, and verify all migrations in a disposable project. The static GitHub Pages app is not connected yet.

The schema creates owner-scoped task, habit, habit-log and life-log tables. RLS policies use `auth.uid()`. Only authenticated access is granted. Task saves, soft deletes and restores use compare-and-swap operations using an expected revision. A stale write returns no row and must be presented as a conflict. Internal privileged functions live in the non-exposed `personal_hq_internal` schema; exposed RPCs use invoker rights. Direct authenticated table writes are revoked so clients cannot bypass task revision checks.

Supabase Auth must disable public sign-ups after creating the owner account; row policies isolate each account, but do not themselves designate which account is the owner. The static client uses the browser-safe publishable key from `life-system/supabase-config.js`; never put a secret/service-role key there. Do not consider the system ready for live data until two-user RLS isolation, wrong-revision behavior, restore/recovery, offline handling, browser-to-browser sync, and privacy scans of the built Pages files are verified. Habit and life-log tables remain read-only until conflict-safe write paths and matching client flows are implemented.
